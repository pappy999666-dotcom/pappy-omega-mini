# Pappy Omega Mini Current Audit Findings

## Omega-v1 reference findings

The VPS contains `/home/ubuntu/omega-v1` and stored forensic audits. The relevant reference requirements are behavioral only; Pappy must retain its own visual language and implementation.

The omega-v1 session-lifecycle audit requires that ACTIVE sessions are never deleted or purged by timeout cleanup, stale cleanup, orphan cleanup, dead-session logic, or reconnect logic. Only terminal states such as LOGGED_OUT, FAILED, or explicit PURGED should be eligible for destructive cleanup. On successful connection, the sequence must be auth complete, session registry persisted, runtime marked ACTIVE, then one WhatsApp and one Telegram connected notification.

The omega-v1 link-preview audit requires preserving already hydrated previews, avoiding fake/manual preview replacement, and allowing Baileys native preview hydration to produce title, description, thumbnail, canonical URL, and high-quality preview where WhatsApp supports it. Status design must enrich the outgoing message before preview hydration and must not replace the designed message with plain text or split it into multiple messages. Long titles should wrap vertically instead of truncating or horizontally compressing. Media captions containing links must remain intact.

## Current Pappy findings

The current per-session Telegram UI is a flat action grid generated by `sessionKeyboard()` in `src/telegram/ui.ts`; existing actions include profile, PFP, create group, name, bio, groups, bridge, group picture, auto-join, join manager, sudo, prefix, health, and purge. Some functions already have secondary callbacks, including profile, PFP, groups, sudo, bridge, and join. The next refactor should expose these as intentional category submenus rather than rendering every operation at the session root.

The current group list handler in `src/telegram/bot.ts` returns a text inventory and supports refresh and leave, but it does not expose a dedicated group-selection/detail submenu for per-group actions.

The current preview manager in `src/preview/preview-manager.ts` performs an 8-second custom HTML metadata fetch and caches the result in Redis. `src/whatsapp/transport-adapter.ts` manually constructs `linkPreview` payloads for group text and mention messages. This can delay outbound responses and may interfere with Baileys native preview hydration. The installed `@crysnovax/baileys` fork has `generateHighQualityLinkPreview: true` by default and native `getUrlInfo()`/`generateWAMessage()` support in its message-send pipeline. The repair should prefer native preview generation for plain URLs and preserve existing hydrated previews; a bounded fallback may be retained only when native hydration is unavailable.

The current link collector uses one shared Redis connection and one sequential `get` + `upsert` per extracted URL. This avoids per-message connection churn but can serialize large link payloads. It is asynchronous from WhatsApp message handling, which is good, but preview fetching remains on the outbound send path for texts containing URLs.

The current startup code hydrates all sessions and starts sessions with persisted auth. It skips only LOGGED_OUT or INVALID auth after the previous fix, so transient ERROR sessions are eligible for restart recovery. Further hardening must ensure successful startup persists ACTIVE state, does not delete ACTIVE records, and avoids duplicate connection/reconnect work. Under many sessions, Mongo and Redis connections should be shared or bounded rather than created per session or per message.

## Installed Baileys facts

The installed fork exposes `GroupStatusContent` with `groupStatus: true`; the direct `sendGroupStatus` socket method is not guaranteed. The current Pappy build therefore falls back to `sendMessage(jid, { ...payload, groupStatus: true })` for group status. Native preview defaults include `generateHighQualityLinkPreview: true` and `linkPreviewImageThumbnailWidth: 192`.
