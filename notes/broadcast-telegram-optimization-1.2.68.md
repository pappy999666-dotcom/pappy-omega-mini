# Broadcast, Preview, Telegram, and Local Session Optimization

**Release:** 1.2.68  
**Date:** 2026-08-22  
**Scope:** PAPPY OMEGA MINI control plane and published panel worker

## Executive result

The published system was audited and the smallest safe optimizations were deployed. The control plane now reports worker package version 1.2.68. Both `pappy-omega-mini.service` and `pappy-panel-v3.service` are active, the private control listener is reachable, and the health endpoint returns successfully.

No WhatsApp message, self-chat, group message, broadcast, or pairing action was generated by this optimization work.

## Group-target resolution

The panel worker already had a persistent encrypted broadcast inventory snapshot and a five-minute freshness window. The remaining cold-start problem was that a broadcast could still wait for `groupFetchAllParticipating()` when a snapshot had expired or the first refresh was slow. The worker now reuses the latest safe non-empty snapshot immediately when a fresh snapshot is unavailable, while starting a background inventory refresh. This makes the first dispatch responsive without performing a second full scan for concurrent commands. The refreshed inventory replaces the snapshot for later jobs.

A job checkpoint remains authoritative for resumed work. This preserves completed-delivery accounting and prevents a restarted broadcast from silently switching target lists mid-run. Inaccessible groups are still handled by the existing confirmed-inaccessibility classification rather than being treated as successful delivery.

## Preview behavior under spam

The worker already cached previews by session and exact source text, but simultaneous identical broadcast commands could each issue a separate control-plane preview request before the first request completed. An in-flight promise map now coalesces identical concurrent requests per session and source text. Successful previews remain cached for 60 seconds, transient preview failures are negatively cached for five seconds, and the worker preview cache is capped at 256 entries to prevent unbounded growth under spam.

The canonical Baileys-native preview pipeline was not changed. In particular, source URL matching, group invite normalization, native preview payload generation, and fallback behavior remain intact. The optimization prevents duplicate resolution work; it does not duplicate WhatsApp replies or broadcast posts.

## Telegram reliability

A top-level Telegraf error boundary was added. It logs the update identifier and error message without creating an unsolicited user reply. This prevents a malformed update or isolated handler exception from becoming an unhandled rejection while preserving the existing command and callback routing. The nonblocking Telegram startup behavior remains in place so polling cannot prevent the 8788 control listener from starting.

## Explicit local-session cleanup

Before cleanup, the database contained nine sessions: seven unassigned local VPS sessions and two panel-assigned sessions. The seven unassigned sessions were removed through the existing scoped application purge path, which stopped local runtime ownership and removed their session records, local auth directories, job/link/traces data, and lifecycle state. The two panel-assigned sessions were not purged, re-paired, or modified.

After cleanup and restart, the database contained two sessions, both panel-assigned; local session count was zero. The panel service remained active throughout the final verification. One panel session was ACTIVE/VALID and the other remained DEGRADED/DEGRADED as it was before this optimization; it was intentionally not touched because the request was to remove only local VPS sessions.

## Remaining limits

The worker still intentionally sends broadcast deliveries through a per-session serial path with the configured delay. Removing that serialization would increase WhatsApp rate-limit and account-risk exposure; the correct optimization is to remove redundant inventory and preview work, not to create uncontrolled concurrent sends. The panel log contained isolated historical Baileys decryption errors, but no evidence in the final window of a new control-plane storm.

The first broadcast for a brand-new session with no persistent inventory remains dependent on the first successful group inventory fetch because there is no safe target list before that fetch. Once the session connects, the worker warms and persists the inventory in the background.
